# Agent guide

## Project and scope

Custom Harley-Davidson ECM firmware for the Hellen Bremen board (Hellen mega-mcu144,
STM32F7, OpenBLT). The root contains board-specific C++ and configuration inputs.
`ext/rusefi/` is a Git submodule pointing to the `P4ulBr4ndt/rusefi` fork; it supplies
the engine-control framework, hardware support, generators, simulator, and tests.
Prefer implementing custom behavior in the root through existing board hooks.

## Essential rules

- **Firmware builds and tests run in CI. Do not attempt local builds or tests.**
  Do not install toolchains, set up Docker, or run simulator/build/test scripts
  unless the user explicitly requests local execution. Existing local helper
  scripts are not the default validation workflow.
- **Never edit, delete, or regenerate generated outputs. CI owns generation.**
  This includes any file or directory whose name contains `autogenerated`
  (case-insensitive), all of root `generated/`, generated directories in the
  submodule, and generated headers, INIs, signatures, and tunes. Files marked
  auto-generated are also off limits regardless of their filename. Read them
  only when needed to understand an interface; change the source input instead.
  Do not run `manual-generate-meta-data.sh` or generators to fix stale outputs.
- Keep changes focused. Preserve existing root and submodule modifications;
  check both repositories before editing. Do not update the submodule revision
  as an incidental part of a feature or fix.
- Do not run `bin/update-rusefi.sh` as routine setup: it executes `git reset --hard`
  inside the submodule and can discard work.

## Where to work

| File(s) | Responsibility |
| --- | --- |
| `board_configuration.cpp` | `setup_custom_board_overrides()` registers defaults, configuration, hardware, CAN, periodic, and TunerStudio callbacks. Start here to trace integration. |
| `board_config.cpp`, `.h` | Defaults, hardware/pin overrides, config sanitization, hardware initialization, TS commands, and configuration-change handling. |
| `board_can.cpp`, `.h` | Harley CAN RX/TX, dashboard data, gear detection, cruise controls, ignition/shutdown requests, fan/pump/purge control, and slow periodic work. |
| `board_etb_control.cpp`, `.h` | Ride modes, engine braking, speed limiting, and electronic throttle (ETB) target slew limits. |
| `board_etb_maps.cpp`, `.h` | Pedal-to-throttle table selection via `pedal2TpsProvider()` and map defaults. |
| `board_instant_accel_shot.cpp`, `.h` | Instant acceleration fuel pulses and fast periodic callback. |
| `board_uds.cpp`, `.h` | UDS diagnostics over CAN/ISO-TP, data identifiers, VIN writes, and reset/programming requests. |
| `board_config.txt` | Custom persistent configuration fields, tables, dimensions, units, scales, and limits. |
| `board_engine_configuration.txt` | Board additions to engine configuration. |
| `prepend.txt` | Generator input defines: table sizes, labels, and TunerStudio visibility options. |
| `board_*.ini` | Handwritten TunerStudio UI fragments: panels, tables, curves, menus, gauges, indicators, and commands. These are editable inputs. |
| `board_types.h`, `knock_config.h`, `default_tune.cpp` | Board types, knock settings, and tune defaults. |
| `board.mk`, `meta-info.env` | Compiled board sources, feature flags, hardware/build settings, board name, CPU, and bootloader selection. |

## Making changes

- Follow surrounding C++ conventions and rusEFI APIs. Trace declarations and
  callers before changing a hook; some integration uses overridden functions
  rather than callbacks in `setup_custom_board_overrides()`.
- For a new tunable, update its schema input, initialization/defaults and
  validation, consuming C++, and relevant handwritten TS fragments together.
  Keep units, scaling, dimensions, and field names consistent. Configuration
  layout changes affect stored tunes and TS definitions; do not hand-adjust
  generated offsets or structures.
- Add new board translation units to `BOARDCPPSRC` in `board.mk`; preserve the
  bootloader guard that excludes application-only sources.
- Preserve timing, sensor validity checks, actuator limits, and shutdown
  behavior when modifying control paths. Follow existing tick/time conversions
  and avoid introducing blocking work into periodic callbacks.
- Search the submodule only for the relevant interface or implementation.
  Useful entry points: `firmware/hw_layer/board_overrides.h`,
  `firmware/controllers/`, `firmware/config/boards/hellen/`,
  `unit_tests/tests/`, and `simulator/` (all under `ext/rusefi/`).
  If a core change is necessary, account for the separate submodule diff and
  commit/revision relationship; a root commit alone does not record its edits.

## Efficient inspection and validation

Start with `git status --short` and `git -C ext/rusefi status --short`.
Search root sources first, excluding dependencies and output trees:

```sh
rg -n 'symbol' -g 'board_*' -g 'prepend.txt' -g 'default_tune.cpp' \
  -g '!ext/**' -g '!generated/**' -g '!build/**' -g '!tmp/**' .
rg -n 'symbol' ext/rusefi/firmware/controllers/actuators \
  -g '!**/*generated*' -g '!**/*autogenerated*'
```

Read targeted sections instead of dumping the dependency tree or generated
files. For local review use `git diff --check`, `git diff --stat`, and the relevant
diffs (including `git -C ext/rusefi diff` when applicable). Review existing tests
and adjust relevant test sources when needed; leave execution to CI. Report
builds/tests as **not run locally; CI validation required** unless CI results
have actually been inspected.

CI entry point: `.github/workflows/build-firmware.yaml`, which delegates to
`ext/rusefi/.github/workflows/custom-board-build/action.yaml` for generation and
builds. It runs on push/manual dispatch; simulator execution is enabled for
`master`/`main`. The root workflow extracts and uploads the board INI and BIN.
`.github/workflows/update-rusefi-reference.yaml` handles scheduled/manual
dependency-reference updates. Inspect CI logs for failures and fix source
inputs; leave generated changes to CI.
